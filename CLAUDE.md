# CLAUDE.md

See AGENTS.md for project rules, structure, state machine and guardrails. Where this file differs from AGENTS.md (Telegram removed, WhatsApp added, new states), this file wins.

## Channels (final design)

- **LinkedIn DMs**: main outreach and conversation channel.
- **Outlook email (Microsoft Graph)**: leads with no LinkedIn profile, plus a formal MoU email when a company is interested.
- **WhatsApp**: owner notifications and message review only. Never used to contact leads.
- **Dashboard "Needs attention"**: backup for anything that needs the owner. Backed by the attention_items table.
- All channels implement the Channel protocol in backend/app/channels/base.py: send_message(thread, text), read_new_replies(since), reply(thread, text).

## Rules

- Every outgoing message passes through a hold window before sending. The window is HOLD_WINDOW_MINUTES (default 10). The owner can approve, edit or cancel during the hold on WhatsApp or the dashboard. If nothing happens, the message is auto-released when hold_until passes.
- DRY_RUN=true by default. Nothing is sent until it is explicitly disabled.
- SEND_ALLOWLIST (comma-separated emails) is a sandbox: when non-empty, email to any other address is logged "blocked by sandbox", the message becomes status `blocked` and is never sent (also in DRY_RUN). Empty means normal behavior. No Gmail anywhere: email is Outlook (Microsoft Graph) only.
- No Telegram anywhere. Do not reintroduce TELEGRAM_* keys or channels/telegram.py.

## States

LinkedIn leads: NEW > QUALIFIED > TARGETED > ENRICHED > DRAFTED > CONNECT_SENT > CONNECTED > DM_SENT > REPLIED.
Email leads skip the connect states: DRAFTED > CONTACTED > REPLIED.
Replies end in INTERESTED, FUTURE_POOL (no opportunity, recheck in 60 days), WRONG_PERSON, NOT_NOW (recheck in 30 days), REPLIED (question or other, owner handles) or UNSUBSCRIBED. No reply after follow-ups on day 4 and day 10 ends in CLOSED.

## Data model additions

- messages: hold_until, review_status (pending_review, approved, cancelled, edited, auto_released), edited_text, reviewed_at, whatsapp_message_id.
- attention_items: id, type (interested, question, channel_error, needs_manual), payload, status (open, resolved, dismissed), created_at.
- notifications_log: id, type, payload, sent_at.
- users: id, email, name, password_hash (null for OAuth accounts), provider (password, microsoft; legacy google rows still load), provider_subject, role (admin, member, viewer, pending, disabled), created_at, last_login_at. Unique on (provider, provider_subject) and on (provider, email). messages.reviewed_by and attention_items.resolved_by point at users.id (set null on delete).

## Dashboard auth (multi-user)

- Accounts: email + password, Sign in with Microsoft (Google sign-in was removed). Accounts are never linked across providers, not even by email: the same address as password and Microsoft makes two accounts, each approved separately. The same provider with the same email but another subject is refused (account_conflict), never taken over.
- Every registration and first OAuth sign-in creates role=pending. Admins approve (default role viewer) in /api/admin/users. The first admin is created only with `python -m app.cli create-admin --email X` (prompts for the password; on an existing password account it promotes it and sets the new password, which also recovers a locked-out owner). No claim from Microsoft ever grants a role.
- Routes (api/auth.py): POST /api/auth/register (202, same answer for a taken email), POST /api/auth/login, POST /api/auth/logout, GET /api/auth/me (also for pending and disabled), GET /api/auth/microsoft/login and /callback. Admin (api/admin_users.py): GET /api/admin/users (?role=), POST /{id}/approve ({role}, pending only), PATCH /{id}/role, POST /{id}/disable, POST /{id}/reset-password (given or generated password; password accounts only; ends that user's sessions). Admins cannot change their own role or disable themselves.
- OAuth (app/auth/oauth.py, authlib): OpenID Connect authorization-code flow with state, nonce and PKCE S256, kept in a signed 10-minute cookie (SessionMiddleware, installed in app/main.py). The callback checks state, exchanges the code with the verifier and validates the ID token (JWKS signature, issuer, audience, expiry, nonce). Any failure redirects to FRONTEND_URL/dashboard?auth_error=<code> without a session. Redirect URI to register with Microsoft: {BACKEND_URL}/api/auth/microsoft/callback. Microsoft multi-tenant values of MS_AUTH_TENANT (common, organizations, consumers) accept any tenant-GUID issuer; a tenant ID restricts sign-in to that tenant. MS_AUTH_* is a separate app registration from MS_CLIENT_ID (Outlook sending).
- Passwords: argon2id, 10 to 128 characters. Login says only "Invalid email or password" for an unknown email, a wrong password, a disabled account or an OAuth-only account, and an unknown email still costs one argon2 verification. Rate limit: 5 per minute per client IP and 5 per minute per email, separately for login and register (in memory, one backend process; the IP comes from CF-Connecting-IP / X-Forwarded-For, so keep the API behind the proxy).
- Session (app/auth/security.py): signed JWT (JWT_SECRET 16+ characters, 12 h) in the httpOnly, SameSite=Lax cookie connectx_session (Secure when APP_ENV=production). It is never returned in a body and never in localStorage; the Authorization header is ignored. The token holds the user id and a fingerprint of the password hash, the role is read from the database on every request, so disabling, a role change or a password reset takes effect immediately. Logout only clears the cookie; there is no server-side session list.
- CSRF: every state-changing request (POST, PUT, PATCH, DELETE) on a protected route, and register, login and logout, needs the header `X-CSRF-Protection: 1`. The API allows no cross-origin requests, so a browser cannot send it from another site.
- Permissions (app/auth/deps.py, the `authorize` dependency on every protected router): viewer reads everything under /api except /api/admin; member also edits, approves and cancels drafts and resolves attention items (the MEMBER_ACTIONS table); admin does everything else that writes (settings, caps, DRY_RUN, pause, channel enable, search queries, generic CRUD) and user management. A new write route is admin-only until added to MEMBER_ACTIONS (a test checks the table against the real routes). pending and disabled get 403 everywhere except /me.
- Audit: dashboard approve, cancel and edit set messages.reviewed_by; attention approve, dismiss and status changes set attention_items.resolved_by. WhatsApp and automatic actions leave it empty.
